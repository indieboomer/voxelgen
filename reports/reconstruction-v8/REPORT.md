# Multi-view voxel reconstruction ? Windows v1.5

A second tool now lives beside the procedural generator. Open **02 / Multi-view reconstruction** in either the browser or the Windows application. Reconstruction is deterministic local TypeScript: no AI, trained model, weights, image-generation endpoint, uploaded files or reconstruction server is involved.

The [analysis and method comparison](ANALYSIS.md) was written before implementation. Orthographic silhouette intersection was selected over photo-consistency, classical feature-based stereo and shading inference because the requested two opposing or four cardinal views do not provide reliable overlapping surface evidence or unknown-camera calibration. Source images supply surface colors; they do not drive any learned inference.

## Using the tool

1. Open the reconstruction tab and try **Load local demo views**, or select your own PNG, JPEG, WebP or BMP images. The demo is a locally ray-rendered asymmetric box sculpture, authored in code specifically to make view direction, holes and front/back markings observable.
2. Choose **Front + back** or **Front + back + left + right**. Use upright, head-on orthographic references of the same object and pose. For photographs, a distant camera with a long focal length approximates this better than a close wide-angle camera. Object boundaries should be visible on every side, against a plain background.
3. Inspect the checkerboard mask previews. **Auto** prefers transparency when the border is transparent; otherwise it estimates a dominant border color and removes matching border-connected pixels using perceptual Lab color distance. Transparent holes remain holes. Enclosed matching regions are kept by default to protect object areas with the background color.
4. If needed, pick the backdrop color, adjust tolerance, or enable **Also remove enclosed matching color** for actual enclosed holes. Use **Paint foreground/background** to correct ambiguous areas. Optional tiny-speck removal, original-image display, mask PNG export and 90-degree rotation are available. Soft shadows or a textured background may need manual correction.
5. Views align automatically using foreground height, horizontal bounding-box center and a shared upright vertical axis. **Shift X/Y**, **Relative scale** and **Flip horizontal** allow corrections. Front is +Z, back -Z, left -X, right +X. The projector already accounts for the natural horizontal reversal of an opposite photograph; Flip is for reference sheets with different mirroring conventions.
6. Set object height in your chosen world units. Choose **Cells across grid** (12?96 per axis) or **World units per voxel**. Grid mode reports the resulting voxel edge. Voxel-size mode preserves the requested edge exactly, with enough cells to enclose the aligned object and a small margin. Sizes requiring fewer than 12 or more than 96 cells are rejected explicitly.
7. For two views, select **Assumed depth / height**. Front/back alone contain no depth measurement; the first implementation uses a straight extrusion restricted by both silhouettes. With four views, side silhouettes constrain depth and this assumption is unused.
8. Press **Reconstruct voxel model**. Segmentation, demo rendering, carving and surface texture projection run in a Web Worker. Progress and cancellation keep the UI responsive.
9. Inspect retained-silhouette percentages, the 3D result and diagnostics. A low percentage indicates conflicts between silhouettes, alignment or grid sampling. A high percentage means consistency with the sampled silhouettes, not proof of accurate hidden geometry. Disconnected parts are retained unless **Keep largest component only** is explicitly enabled.
10. Export **Voxel JSON**, **Textured GLB**, **Texture atlas PNG**, or **Save project**. Projects contain local PNG copies of all images, mask settings, run-length encoded brush corrections, alignment and reconstruction controls. Open project restores them. Input changes disable geometry exports until a new reconstruction is built, preventing an old model from being mistaken for the current inputs.

## Geometry, color and scale

The algorithm back-projects each foreground mask onto a cubic voxel grid and intersects the constraints. Pixel-center-aware bilinear mask sampling avoids a one-sample directional bias when opposing views meet an exact pixel boundary. Four-view reconstruction constrains X/Y and Z/Y projections; front/back-only mode also clips to the explicit depth interval. Six-connected component analysis reports detached pieces and optionally keeps the largest.

Voxel JSON uses the workshop's version 1 grid/palette format, with a `reconstruction` metadata object containing world scale, voxel edge, source view names, mask/alignment settings, assumptions and consistency diagnostics. Palette colors are deterministically quantized to a 6 ? 6 ? 6 RGB cube. Colors are selected using the closest visible cardinal boundary along the voxel's projected ray. A voxel has one palette entry, so corners cannot store several different face colors in this format.

GLB preserves finer source colors with a new per-quad texture atlas. Each surface direction uses its matching source view when available; other directions use an explicit extrapolation from an available image. Background pixels are excluded from edge sampling. Atlas texels sample the source image projected across the face, with a one-pixel gutter and texel-center UVs. White mesh tint avoids multiplying the source color twice. The preview disables atlas mipmaps to avoid island bleed, uses unmodified source RGB as base color, and adds ordinary scene lighting. Directional illumination from an input photograph is not removed.

Choose exposed voxel faces or material-aware greedy rectangles; both represent the same occupancy. Triangle-edge display is for inspection and is removed from GLB export. GLB vertex coordinates use world scale. Voxel cell coordinates are `(index + 0.5) * voxelSize - worldSide / 2`; the metadata is needed to recover those units from voxel JSON. Voxel sampling can shift the visible surface by roughly half a cell.

A reconstructed object is fixed voxel data, not a searched procedural family recipe. It has voxel/model exports rather than pretending that the image inputs produced a reusable recipe. The existing generator remains a separate tool with its original Rust/TypeScript recipe exports.

## Scope and limits

This is a visual hull, not general photogrammetry. Recesses invisible in every silhouette, unseen top/bottom geometry and internal cavities are underdetermined. A concave object can therefore reconstruct too full. Opposing views alone can give a slab-like extrusion; depth is supplied by the user. Four side views improve the constraint but still do not remove that ambiguity. The [visual hull literature](https://www.sciencedirect.com/science/article/pii/S1077314296905081) describes this limitation; calibrated [photo-consistency methods](https://publications.ri.cmu.edu/a-theory-of-shape-by-space-carving) solve a different, stronger input problem.

Perspective calibration, arbitrary camera angles, pose changes, automatic shadow removal, intrinsic material/lighting separation and hidden-shape invention are not implemented. Mask correction and alignment controls expose those uncertainties instead of concealing them. The view images are resized locally to at most 768 pixels on the longest side, preserving aspect ratio; file inputs are limited to 25 MB, and projects to 40 MB. A 100,000-quad surface limit prevents unusually noisy masks from creating excessive atlas allocations. Imported voxel JSON can now contain grids up to 96; procedural recipe generation retains its original 12?48 bound.

## Verification

- [Pure-code checks](verification.json): eight background/alpha/manual-mask cases; known cuboids at grids 16, 24, 32, 48, 64 and 96; ground-truth voxel IoU above 0.9; every occupied cell inside all silhouettes; opposite-view orientation; four independent directional surface colors; deterministic voxels/atlas pixels; physical voxel sizing and scale invariance; two-view depth changes; invalid/conflicting inputs; disconnected-part retention and optional cleanup; greedy reduction; compatible voxel parser round trips.
- [Browser checks](browser.json): demo and four actual PNG file inputs, eyedropper and painted erasure, exact voxel export, independent GLB import, exact atlas PNG pixels, world-scale metadata, wireframe isolation, two-view and voxel-size controls, embedded-image project reload, cancellation and restart, mobile width, and generator-tab preservation. Zero external requests and zero image-service requests were observed.
- [Native Windows checks](desktop.json): custom application protocol, real file input, isolated profile without an API key, worker responsiveness, exact 48? voxel export, textured GLB and PNG saves through native dialogs, project save/reload and generator switching. The main-process remote-fetch counter and renderer external-request log were both zero.
- Existing browser voxel/greedy checks passed for all three rock families, including downloaded Rust compilation, standalone TypeScript matches, GLB imports and imported grids. Existing 72 source/compiled-runtime comparisons passed.
- [Performance measurements](performance.json): Windows x64, Node 24.14.1, Intel Core i9-10900F; four 192? demo views; three repetitions per grid, with median and p95 recorded separately for segmentation, carving/coloring and mesh/atlas construction. The 96? case measured median ~68 ms segmentation, ~86 ms carving/coloring and ~217 ms meshing/atlas. These are small synthetic inputs on this machine, not a claim of single-frame performance or a guarantee for arbitrary photographs. Demo image rendering and browser image decoding are excluded from these stage timings.
- [Portable build verification](release.json) records the activated Windows build and verifies its packaged application archive against the tested native build.

Run `npm run check:reconstruction`, `npm run check:reconstruction:browser`, and `npm run check:reconstruction:desktop`. The last test uses the latest packaged executable and an isolated QA profile. Use `node --import tsx scripts/reconstruction-benchmark.ts` for the stage benchmark.

Source modules live in `src/reconstruction/`: `background.ts` (segmentation), `core.ts` (projection/carving), `texture.ts` (color atlas), `worker.ts` (local execution/cancellation boundary), `ui.ts` (application adapter), `demo.ts` (authored test views), and `types.ts` (data contracts).
